# Το χρονόμετρο των δοκιμών

## Τι μετράω

Το εργαλείο μετράει τον χρόνο που απαιτείται για την επίλυση των τεχνικών προβλημάτων SEO ενός website κατά τη διάρκεια μιας πειραματικής δοκιμής.

Συγκεκριμένα, μετράει τον **καθαρό χρόνο**, δηλαδή τον χρόνο που έχει παρέλθει από την έναρξη της δοκιμής, αφαιρώντας τα χρονικά διαστήματα κατά τα οποία το χρονόμετρο βρίσκεται σε παύση.

Δεν μετράει τον πραγματικό χρόνο εργασίας, καθώς δεν παρακολουθεί τις ενέργειες ή τη δραστηριότητα του χρήστη. Επομένως, ο χρόνος συνεχίζει να καταγράφεται ακόμη και όταν δεν πραγματοποιείται κάποια ενέργεια, εκτός εάν ενεργοποιηθεί η παύση.

Η μέτρηση πραγματοποιείται διαδοχικά:
- Η πρώτη διόρθωση χρεώνεται με τον χρόνο από την έναρξη της δοκιμής μέχρι την επίλυσή της.
- Κάθε επόμενη διόρθωση χρεώνεται με τον χρόνο από την επίλυση της προηγούμενης μέχρι τη δική της επίλυση.

Με αυτόν τον τρόπο, προκύπτει τόσο ο συνολικός καθαρός χρόνος μέχρι την επίλυση κάθε προβλήματος όσο και η καθαρή χρονική διάρκεια μεταξύ διαδοχικών διορθώσεων.

Η διάγνωση και ο εντοπισμός των προβλημάτων δεν περιλαμβάνονται στη μέτρηση, καθώς έχουν πραγματοποιηθεί πριν από την έναρξη των πειραματικών δοκιμών. Σκοπός είναι να μετρηθεί ο χρόνος που απαιτείται για την εφαρμογή των διορθώσεων και να συγκριθούν οι δύο πειραματικές σειρές υπό κοινές συνθήκες.

## Πώς κατέληξα σε αυτόν τον τρόπο

Αρχικά, η καταγραφή του χρόνου θα μπορούσε να γίνει χειροκίνητα, με τον χρήστη να σημειώνει πότε ολοκληρώνεται κάθε διόρθωση. Ωστόσο, αυτή η προσέγγιση παρουσιάζει ένα σημαντικό πρόβλημα: η χρονική στιγμή ολοκλήρωσης εξαρτάται από την ανθρώπινη αντίδραση και την ακρίβεια της χειροκίνητης καταγραφής.

Για να περιοριστεί αυτό το πρόβλημα, αναπτύχθηκε ένας μηχανισμός αυτόματης επαλήθευσης της ολοκλήρωσης των διορθώσεων.

Ο αυτόματος έλεγχος επιλύει δύο βασικά ζητήματα:

1. **Αντικειμενικότητα:** Δεν χρειάζεται ο χρήστης να αποφασίσει πότε μια διόρθωση θεωρείται ολοκληρωμένη. Το εργαλείο ελέγχει αυτόματα αν ικανοποιείται η αντίστοιχη τεχνική συνθήκη.
2. **Ακρίβεια καταγραφής:** Η χρονική στιγμή καταγράφεται αυτόματα, περιορίζοντας την απόκλιση που θα υπήρχε με τη χειροκίνητη καταγραφή.

Επιπλέον, η αυτοματοποίηση επιτρέπει την παρακολούθηση πολλών διορθώσεων ταυτόχρονα, χωρίς να χρειάζεται ο χρήστης να διακόπτει την εργασία του για να καταγράφει την ολοκλήρωση καθεμιάς.

## Πώς λειτουργεί

Η εφαρμογή αποτελείται από δύο βασικά μέρη: τον μηχανισμό αυτόματων ελέγχων (`checks.py`) και το γραφικό περιβάλλον του χρονομέτρου (`timer_app.py`).

### Τι κάνω εγώ σε μια δοκιμή, βήμα-βήμα

1. Ανοίγω το γραφικό περιβάλλον εκτελώντας:

   ```bash
   python src/timer_app.py
   ```

2. Συμπληρώνω το πεδίο **Site** με τη διεύθυνση του clone που πρόκειται να δοκιμαστεί.
3. Συμπληρώνω το πεδίο **Κλώνος** με ένα όνομα αναγνώρισης, π.χ. `clone1`.
4. Συμπληρώνω προαιρετικά το πεδίο **Audit id**, για να ορίσω από ποιο audit θα αντληθούν τα URLs με σφάλματα 4xx. Αν το πεδίο παραμείνει κενό, χρησιμοποιείται το πιο πρόσφατο audit.
5. Επιλέγω την πειραματική σειρά:
   - `model`
   - `semrush`
   - `practice` (δοκιμαστικό πέρασμα).
6. Πατάω **Start** για να ξεκινήσει η δοκιμή και η μέτρηση του χρόνου.
7. Εργάζομαι πάνω στις τεχνικές διορθώσεις, ενώ το εργαλείο ελέγχει αυτόματα την κατάστασή τους.
8. Χρησιμοποιώ το **Pause** όταν χρειάζεται να διακοπεί προσωρινά η μέτρηση, όπως κατά την αναμονή για την ολοκλήρωση ενός re-audit ή κατά τη διάρκεια διαλειμμάτων.
9. Χρησιμοποιώ το **Σημείωση** για να καταγράψω κάποιο γεγονός ή σχόλιο μαζί με τη χρονική στιγμή του.
10. Όταν ολοκληρωθεί η δοκιμή, πατάω **Stop** για να αποθηκευτούν τα αποτελέσματα.

### Τι κάνει μόνο του το εργαλείο

Μετά το πάτημα του Start, το εργαλείο εκτελεί αρχικά έναν έλεγχο του clone.

Σκοπός είναι να διαπιστώσει αν το δοκιμαστικό αντίγραφο περιέχει πράγματι τα προβλήματα που πρόκειται να διορθωθούν. Αν κάποια προβλήματα απουσιάζουν ήδη, εμφανίζει προειδοποίηση, καθώς αυτό μπορεί να επηρεάσει την εγκυρότητα της δοκιμής.

Στη συνέχεια:

- Ελέγχει αυτόματα τις ανοιχτές διορθώσεις κάθε 15 δευτερόλεπτα.
- Όταν μια διόρθωση ικανοποιήσει την αντίστοιχη συνθήκη σε δύο συνεχόμενους ελέγχους, θεωρείται ολοκληρωμένη.
- Καταγράφει ως χρόνο ολοκλήρωσης τη χρονική στιγμή του πρώτου επιτυχημένου ελέγχου.
- Παράγει ηχητική ειδοποίηση όταν εντοπίζει μια ολοκληρωμένη διόρθωση.
- Εμφανίζει την πρόοδο των διορθώσεων, για παράδειγμα 12/19 για την F01.
- Αν κάποια διόρθωση είναι ήδη λυμένη κατά την έναρξη, καταγράφει αυτή την κατάσταση.
- Αν ένας έλεγχος αποτύχει λόγω προβλήματος σύνδεσης ή επειδή το site δεν απαντά, η διόρθωση θεωρείται μη λυμένη στον συγκεκριμένο γύρο και ελέγχεται ξανά στον επόμενο.

Οι δύο συνεχόμενοι επιτυχημένοι έλεγχοι χρησιμοποιούνται ώστε να μειωθεί η πιθανότητα να θεωρηθεί μια διόρθωση ολοκληρωμένη εξαιτίας ενός προσωρινού ή τυχαίου αποτελέσματος.

### Τι ελέγχεται για κάθε διόρθωση (F01–F06)

Κάθε διόρθωση διαθέτει ένα πεδίο `check` στο αρχείο `catalog/fixes.yaml`, το οποίο ορίζει την τεχνική συνθήκη που πρέπει να ικανοποιείται για να θεωρηθεί λυμένη.

| Κωδικός | Διόρθωση | Τι ελέγχει το εργαλείο |
|---|---|---|
| F01_routing | Κανόνες rewrite | Ελέγχει τα 19 URLs που είχαν εντοπιστεί με σφάλματα 4xx στο audit. Τα `/σχετικα/` και `/en/home/` περιλαμβάνονται ήδη σε αυτά. Αφαιρεί τυχόν διπλότυπα και απαιτεί όλα τα URLs να επιστρέφουν HTTP 200. |
| F02_browser_caching | Cache-Control | Ελέγχει τα CSS και JavaScript αρχεία του ίδιου του website που φορτώνει η αρχική σελίδα. Όλα πρέπει να διαθέτουν κεφαλίδα `Cache-Control`. Τα αρχεία από εξωτερικά domains εξαιρούνται. |
| F03_hsts | HTTP Strict Transport Security | Ελέγχει αν η αρχική σελίδα επιστρέφει την κεφαλίδα ασφαλείας `Strict-Transport-Security` (HSTS). |
| F04_home_meta_description | Meta Description | Ελέγχει αν η αρχική σελίδα διαθέτει μη κενό meta description. |
| F05_home_content | Περιεχόμενο και αναλογία κειμένου προς HTML | Ελέγχει αν η αρχική σελίδα περιέχει τουλάχιστον 200 λέξεις και αν η αναλογία κειμένου προς HTML υπερβαίνει το 10%. |
| F06_llms_txt | llms.txt | Ελέγχει αν το αρχείο `/llms.txt` είναι διαθέσιμο και επιστρέφει HTTP 200. |

**Σημαντικό:** Οι έλεγχοι αυτοί αποτελούν τεχνικές προσεγγίσεις των αντίστοιχων κριτηρίων του Semrush και όχι πλήρη αναπαραγωγή του αλγορίθμου του. Επομένως, η τελική επιβεβαίωση της επίλυσης των προβλημάτων γίνεται μέσω νέου audit.

## Τι αποθηκεύεται

Όταν πατήσω Stop, το εργαλείο αποθηκεύει δύο αρχεία στον φάκελο `data/timings/`.

### 1. Αρχείο καταγραφής γεγονότων (events)

Περιλαμβάνει το αναλυτικό ιστορικό της δοκιμής:
- Τις ενέργειες που πραγματοποιήθηκαν κατά τη διάρκειά της.
- Τις χρονικές στιγμές των γεγονότων.
- Τις σημειώσεις που προστέθηκαν χειροκίνητα.
- Τα γεγονότα που σχετίζονται με την ολοκλήρωση των διορθώσεων.
- Τις σχετικές ενέργειες του χρονομέτρου, όπως Start, Pause και Stop.
- Την αρχική κατάσταση κάθε διόρθωσης.
- Κάθε αλλαγή στην πρόοδο των διορθώσεων, μαζί με τη χρονική στιγμή της, π.χ. από 12/19 σε 15/19.

Η καταγραφή των αλλαγών στην πρόοδο επιτρέπει τη μεταγενέστερη ανασύνθεση της εξέλιξης της δοκιμής και τη δημιουργία καμπύλης που θα δείχνει πόσα προβλήματα, σταθμισμένα με τη σοβαρότητά τους, έχουν λυθεί ανά χρονικό διάστημα. Ο υπολογισμός θα βασιστεί στις στιγμές επίλυσης, στις σχέσεις `resolves` και στα βάρη σοβαρότητας που ορίζονται στον κατάλογο διορθώσεων.

### 2. Αρχείο σύνοψης (`..._summary.csv`)

Περιλαμβάνει μία εγγραφή για κάθε διόρθωση και αποθηκεύει:

- **Χρόνο επίλυσης:** Τη χρονική στιγμή κατά την οποία αναγνωρίστηκε η ολοκλήρωση της διόρθωσης.
- **Καθαρό χρόνο από την αρχή:** Τον συνολικό καθαρό χρόνο που έχει παρέλθει από την έναρξη της δοκιμής μέχρι την επίλυση της συγκεκριμένης διόρθωσης.
- **Καθαρή διάρκεια από την προηγούμενη λύση:** Τον χρόνο που μεσολάβησε από την ολοκλήρωση της προηγούμενης διόρθωσης.
- **Σειρά επίλυσης:** Τη σειρά με την οποία ολοκληρώθηκαν οι διορθώσεις.
- **Κατάσταση κατά την έναρξη:** Αν η διόρθωση ήταν ήδη λυμένη όταν ξεκίνησε η δοκιμή.

Οι διορθώσεις που δεν ολοκληρώθηκαν καταγράφονται επίσης στο αρχείο, μαζί με τον λόγο για τον οποίο δεν θεωρήθηκαν λυμένες.

Με αυτόν τον τρόπο, διατηρείται τόσο το αναλυτικό ιστορικό της δοκιμής όσο και μια συνοπτική καταγραφή των αποτελεσμάτων που θα χρησιμοποιηθούν στη σύγκριση των δύο πειραματικών σειρών.

## Όρια

### Ακρίβεια μέτρησης

Το εργαλείο πραγματοποιεί ελέγχους κάθε 15 δευτερόλεπτα.

Επομένως, η πραγματική στιγμή επίλυσης μιας διόρθωσης δεν είναι γνωστή με απόλυτη ακρίβεια. Καταγράφεται η χρονική στιγμή του πρώτου επιτυχημένου ελέγχου, η οποία μπορεί να απέχει έως και 15 δευτερόλεπτα από την πραγματική στιγμή ολοκλήρωσης.

Παρότι απαιτούνται δύο συνεχόμενοι επιτυχημένοι έλεγχοι για την επιβεβαίωση της επίλυσης, ως χρόνος ολοκλήρωσης χρησιμοποιείται η στιγμή του πρώτου επιτυχημένου ελέγχου και όχι του δεύτερου.

Η ίδια διαδικασία εφαρμόζεται και στις δύο πειραματικές σειρές, ώστε να διατηρείται η συνέπεια της μέτρησης.

### Διαμοιρασμός του χρόνου μεταξύ διορθώσεων

Επειδή η διάρκεια κάθε διόρθωσης υπολογίζεται από την επίλυση της προηγούμενης, ο τρόπος με τον οποίο κατανέμεται ο χρόνος έχει ορισμένες ιδιαιτερότητες.

- **Ταυτόχρονη επίλυση δύο διορθώσεων:** Αν μία ενέργεια οδηγήσει στην ταυτόχρονη επίλυση δύο προβλημάτων, η πρώτη διόρθωση λαμβάνει τον χρόνο που έχει παρέλθει από την προηγούμενη λύση, ενώ η δεύτερη λαμβάνει μηδενική ή σχεδόν μηδενική διάρκεια. Αυτό είναι επιθυμητό, καθώς αποτυπώνει την επικάλυψη μεταξύ των διορθώσεων.
- **Παράλληλη εργασία σε δύο διορθώσεις:** Αν πραγματοποιείται εργασία πάνω σε δύο προβλήματα παράλληλα, ο χρόνος καταγράφεται με βάση τη σειρά με την οποία επιβεβαιώνεται η επίλυσή τους και όχι με βάση τον πραγματικό χρόνο εργασίας που αφιερώθηκε σε καθένα ξεχωριστά.

Επομένως, η διάρκεια ανά διόρθωση δεν πρέπει να ερμηνεύεται ως ο αποκλειστικός χρόνος εργασίας που απαιτήθηκε για την επίλυσή της, αλλά ως το χρονικό διάστημα μεταξύ διαδοχικών ολοκληρώσεων.

### Παύσεις

Η λειτουργία Pause χρησιμοποιείται για την εξαίρεση χρονικών διαστημάτων κατά τα οποία δεν επιθυμείται να συνεχίζεται η μέτρηση.

Ενδεικτικά, περιλαμβάνει:
- Την αναμονή για την ολοκλήρωση ενός re-audit.
- Τα διαλείμματα κατά τη διάρκεια της δοκιμής.

Ο ακριβής ορισμός των περιπτώσεων που δικαιολογούν παύση και η συνεπής εφαρμογή του θα καθοριστούν στο `protocol.md`, ώστε να ισχύουν οι ίδιες συνθήκες και στις δύο πειραματικές σειρές.

### Αποτυχίες σύνδεσης

Αν το website δεν απαντήσει σε έναν έλεγχο, η αντίστοιχη διόρθωση θεωρείται μη λυμένη στον συγκεκριμένο γύρο ελέγχου και ελέγχεται ξανά στον επόμενο.

Αυτό σημαίνει ότι ένα προσωρινό πρόβλημα σύνδεσης δεν οδηγεί αυτόματα στην καταγραφή μιας διόρθωσης ως ολοκληρωμένης. Ωστόσο, μπορεί να καθυστερήσει την επιβεβαίωση της πραγματικής επίλυσής της.

### Διορθώσεις που χαλάνε ξανά

Μια διόρθωση που έχει ήδη σημειωθεί ως λυμένη δεν ελέγχεται ξανά από το εργαλείο.

Επομένως, αν μια μεταγενέστερη αλλαγή αναιρέσει μια προηγούμενη διόρθωση, το εργαλείο δεν θα το εντοπίσει. Για παράδειγμα, μια αλλαγή στο `.htaccess` για την F02 μπορεί να επηρεάσει τους κανόνες rewrite της F01, προκαλώντας την επανεμφάνιση προβλημάτων στα URLs.

Η συγκεκριμένη περίπτωση εντοπίζεται μέσω του τελικού re-audit, το οποίο επιβεβαιώνει την τελική κατάσταση του website.

### Διαφορές από το Semrush

Οι αυτόματοι έλεγχοι δεν αναπαράγουν πλήρως τη μεθοδολογία του Semrush.

Για παράδειγμα:
- Το F05 χρησιμοποιεί δικό του υπολογισμό λέξεων και αναλογίας κειμένου προς HTML, ο οποίος αποτελεί προσέγγιση του αντίστοιχου κριτηρίου.
- Το F02 εξετάζει την παρουσία της κεφαλίδας `Cache-Control`, όχι απαραίτητα όλες τις παραμέτρους ή τη σωστή διάρκεια προσωρινής αποθήκευσης.
- Οι έλεγχοι F02–F05 εξετάζουν μόνο την αρχική σελίδα, ενώ το Semrush ελέγχει όλες τις σελίδες που εντοπίζει. Για την F04 αυτό είναι συμβατό με το αντικείμενο της διόρθωσης, καθώς αφορά αποκλειστικά την αρχική σελίδα. Για τις F02 και F05, η περιορισμένη κάλυψη ενδέχεται να μην αποτυπώνει προβλήματα που εμφανίζονται σε άλλες σελίδες.
- Τα υπόλοιπα checks επιβεβαιώνουν συγκεκριμένες τεχνικές συνθήκες και όχι ολόκληρη τη διαδικασία αξιολόγησης του Semrush.

Για αυτόν τον λόγο, οι έλεγχοι χρησιμοποιούνται για τη συνεπή καταγραφή του χρόνου και όχι ως υποκατάστατο του τελικού SEO audit.

### Δίκαιη σύγκριση των δύο πειραματικών σειρών

Για να είναι αξιόπιστη η σύγκριση, πρέπει να διασφαλιστεί ότι:

- Και οι δύο σειρές ξεκινούν από clone που παρουσιάζει τα ίδια αρχικά προβλήματα.
- Χρησιμοποιείται το ίδιο εργαλείο χρονομέτρησης.
- Εφαρμόζονται οι ίδιες συνθήκες αυτόματου ελέγχου.
- Η διαδικασία καταγραφής και παύσης του χρόνου είναι κοινή.
- Η ολοκλήρωση των διορθώσεων αξιολογείται με τα ίδια τεχνικά κριτήρια.
- Οι διορθώσεις που είναι ήδη λυμένες κατά την έναρξη αναγνωρίζονται και λαμβάνονται υπόψη κατά την ανάλυση των αποτελεσμάτων.
- Οι περιπτώσεις αποτυχίας σύνδεσης αντιμετωπίζονται με τον ίδιο τρόπο.
- Οι περιπτώσεις στις οποίες μία διόρθωση επηρεάζει την κατάσταση μιας άλλης καταγράφονται και ελέγχονται μέσω του τελικού re-audit.

Έτσι, η διαφορά στους χρόνους μπορεί να αποδοθεί με μεγαλύτερη αξιοπιστία στις διαφορετικές πειραματικές συνθήκες και όχι σε διαφορετικό τρόπο μέτρησης.

## Τι μένει

Πριν πραγματοποιηθεί η πρώτη πραγματική δοκιμή, απαιτούνται τα εξής:

1. Ενσωμάτωση των νέων αρχείων στο project και έλεγχος των αλλαγών στο `fixes.yaml`, ώστε να επιβεβαιωθεί ότι δεν έχουν χαθεί προηγούμενες ρυθμίσεις.
2. Εκτέλεση του `checks.py` στο πραγματικό website:

   ```bash
   python src/checks.py --site https://edge.dmsm2026.neuroverse.gr
   ```

3. Έλεγχος των αποτελεσμάτων για να διαπιστωθεί αν οι αυτοματοποιημένοι έλεγχοι αναγνωρίζουν σωστά την υφιστάμενη κατάσταση του website.
4. Διόρθωση τυχόν λανθασμένων αποτελεσμάτων των checks.
5. Επιβεβαίωση ότι το clone περιέχει τα προβλήματα που πρόκειται να διορθωθούν πριν από την έναρξη κάθε πειραματικής δοκιμής.
6. Commit των αλλαγών στο GitHub.

Μετά την επιτυχή ολοκλήρωση αυτών των βημάτων, θα πραγματοποιηθεί η πρώτη πραγματική δοκιμή του χρονομέτρου.

Τα τελικά χαρακτηριστικά της διαδικασίας θα καταγραφούν στο `protocol.md`, ενώ οι σχετικές σχεδιαστικές επιλογές θα τεκμηριωθούν ως Απόφαση 11 στο `decisions.md`.
